## 结论

这条链路已经适合作为“系统能力强弱”的回归基线。

原因：

- 它覆盖了从立项到导出的完整主链路，而不是单点 API。
- 它已经包含“评估 -> 问题单 -> 修订 -> 应用”的质量回路。
- 它把章节数、题材、篇幅约束固定住了，适合未来横向比较。

但它当前还不能作为“发表级作品达标”的充分证明。

原因：

- 导出结果里出现了明显的段落重复与内容回灌。
- 评估分数不低，但没有有效识别重复段落与结构性冗余。
- 文学质量仍偏“可读草稿”，距离“发表级成稿”还有明显差距。

## 本次暴露出的核心问题

### 1. 导出文本存在明显重复段落

从导出的小说样本看，第一章和第二章都出现了成段内容重复、意象重复、信息重复的问题。这说明当前系统虽然能完成“生成 + 修订”，但在版本应用或修订替换阶段，存在把旧内容与新内容共同保留的风险。

建议：

- 在修订应用前后增加段落级 diff 检查。
- 对同章正文做重复段落检测，如果相似度高于阈值则阻止直接通过。
- 将“重复率”纳入评估分数和导出前质量门禁。

### 2. 评估器对“重复与回灌”识别不足

本次两章评估得分分别为 87 和 86，但导出内容里仍有肉眼可见的重复块。这说明当前评估更偏向“局部语感与常规问题”，对结构性重复、同义回灌、段落复写的检出能力不够。

建议：

- 新增“章节重复率”“段落相似度峰值”“重复意象密度”三个指标。
- 将重复检测做成硬门禁，而不是软建议。
- 评估报告里单列“结构性重复”问题类型，不能只混在风格或节奏里。

### 3. 修订链路虽然闭环，但修订目标仍不够精确

本次 8 个问题单都完成了修订并应用，说明流程通了；但从导出结果看，修订更像“生成了一版替代文本”，而不总是“精确修补问题所在段落”。这会导致修订收益不稳定，并放大重复风险。

建议：

- issue 创建时尽量绑定更准确的 `locationRef` 与原文摘录。
- 修订优先做段落级替换，不要默认回退到整章或首段替换。
- 应用修订后，自动复评该章，确认问题确实收敛而不是转移。

### 4. “两章基线”目前需要脚本手动删除默认章节

创建项目时系统会自动生成一个默认章节，这会干扰固定章节数的基线测试。当前脚本通过先删除默认章节，再导入两章来维持稳定。

建议：

- 在项目创建接口增加可选项：`createDefaultChapter: false`。
- 或在“从大纲导入章节”接口增加 `replaceExisting: true` 模式。
- 让“固定 2 章基线”变成系统原生能力，而不是脚本绕行。

### 5. 篇幅控制接近目标，但仍需更稳

本次导出总字数 5865，已经接近 6000 字目标，说明整体长度控制可用。但如果后续模型波动变大，仍可能偏离较多。

建议：

- 让 outline 阶段明确每章目标字数，例如每章 2800-3200。
- 让场景规划时同步分配场景字数预算。
- 在正文生成后，若低于目标下限，增加“补足篇幅但不灌水”的二次扩写阶段。

### 6. “发表级”目标需要独立质量门禁

目前流程跑通，不代表文本已经达到发表级。发表级需要额外的标准：语言密度、人物辨识度、冲突递进、叙事新鲜度、句式控制、意象统一、结尾余韵等，而这些并没有被当前基线充分约束。

建议：

- 新增“发表准备度评估”阶段，独立于现有章节评估。
- 输出明确分项，例如：
  - 语言成熟度
  - 人物辨识度
  - 冲突推进质量
  - 结构完整度
  - 重复与模板痕迹
  - 结尾余韵
- 未达到阈值时，不应把导出结果视为“达标基线”。

## 对未来基线的建议

建议把这条测试正式命名为：

`武侠短篇两章质量闭环基线`

建议固定输入条件：

- 题材固定为武侠
- 固定 2 章
- 目标 6000 字左右
- 固定走“评估 -> 问题单 -> 修订 -> 应用 -> 导出”全链路

建议固定验收指标：

- 总章节数必须为 2
- 每章至少 2 个场景
- 必须成功生成初始版本
- 每章必须成功评估
- 问题单修订成功率应达到 90% 以上
- 导出必须成功
- 总字数应在 5000-7000 区间
- 重复段落率应低于预设阈值

建议固定输出物：

- 小说 markdown
- 结构化 JSON 报告
- 质量摘要 markdown

## 优先级最高的优化项

1. 给导出前增加重复段落检测与阻断。
2. 给评估器增加“结构性重复”硬指标。
3. 让修订绑定准确段落，不要频繁回退到粗粒度替换。
4. 让项目创建或章节导入支持“无默认章节 / 替换导入”。
5. 新增“发表准备度”独立评估，不把跑通闭环误判为文学质量达标。

## 结语

这条基线已经足够好，适合成为未来版本比较强弱的核心回归测试。

但如果目标是“发表级优秀作品”，那么下一阶段的重点不再是“能不能跑通”，而是“能不能稳定避免重复、提升文学完成度，并把发表级判断前置成明确门禁”。
## 新一轮门禁调参结论

### 1. 修订长度门禁改为混合策略

上一轮的纯比例门禁对超短片段过于敏感，容易把合理补全误判为失败。建议固定采用“短文本绝对差值 + 长文本比例”的混合策略：

- 原文较短时，优先使用最小绝对字数差门限，允许必要补全。
- 原文较长时，继续使用保留率与膨胀率，防止整章缩水或灌水。
- `append` 模式单独放宽，不与 `replace` 共用同一套阈值。

### 2. 导出门禁必须返回可定位样本

导出门禁除了返回失败结论，还应明确返回：

- 问题类型，例如字数不足或重复段落。
- 触发章节。
- 重复段落样本。

这样基线脚本才能把问题结构化写入报告，后续也更容易区分是模型波动、修订链路问题，还是门禁阈值过严。

### 3. 基线报告要保留失败分类

建议把以下失败类型作为固定维度沉淀到每次基线报告中：

- `revision_too_short`
- `revision_too_long`
- `duplicate_paragraph`
- `length_gate`
- `export_gate`
- `other`

未来比较不同版本时，不只看“有没有失败”，还要看“失败结构有没有收敛”，这比单纯的通过率更能反映系统能力变化。

### 4. 回归标准升级为双层验收

建议未来把这条武侠两章基线拆成两层：

- 流程闭环验收：10 步主链路完整跑通，每章完成评估，问题单修订成功率达到阈值。
- 质量门禁验收：导出总字数达到下限，不命中重复段落，修订失败主要收敛在少量可解释类别内。

只有两层都通过，才算真正的基线达标。
